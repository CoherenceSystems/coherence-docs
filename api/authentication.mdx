Every request to the Coherence Atlas API must be authenticated with an API key. Keys are passed as Bearer tokens in the `Authorization` request header. There are no session cookies or OAuth flows — each request is independently authenticated, making the API straightforward to use from scripts, pipelines, and server-side applications.

## Obtaining Your API Key

Generate an API key from the Coherence Atlas dashboard:

<Steps>
  <Step title="Open Settings">
    Navigate to **Settings** in the Coherence Atlas dashboard sidebar.
  </Step>
  <Step title="Go to API Keys">
    Select the **API Keys** tab to view existing keys and create new ones.
  </Step>
  <Step title="Create a New Key">
    Click **Generate Key**, give it a descriptive label (e.g., `prod-ingest`, `ci-readonly`), and select the appropriate scope.
  </Step>
  <Step title="Copy and Store the Key">
    Copy your key immediately — it is displayed only once. Store it in a secrets manager or environment variable.
  </Step>
</Steps>

<Warning>
  Your API key is shown in full only at creation time. If you navigate away without copying it, you will need to generate a new one.
</Warning>

## Passing the Key in a Request

Include your API key as a `Bearer` token in the `Authorization` header of every request:

```
Authorization: Bearer <your-api-key>
```

**Example request:**

```bash
curl -X GET https://api.coherencesystems.net/v1/signals \
  -H "Authorization: Bearer ca_live_abc123xyz789" \
  -H "Content-Type: application/json"
```

All requests must also be made over **HTTPS**. HTTP requests are rejected.

## Key Scopes

When generating a key, you select a scope that controls what the key can access:

<CardGroup cols={2}>
  <Card title="Read-Only" icon="eye">
    Permits `GET` requests only. Use for dashboards, monitoring pipelines, and any context where write access is not required.
  </Card>
  <Card title="Read-Write" icon="pen-to-square">
    Permits `GET`, `POST`, `PATCH`, and `DELETE` requests. Use for ingestion pipelines, review management, and artifact creation.
  </Card>
</CardGroup>

<Tip>
  Follow the principle of least privilege — issue read-only keys for consumers that only need to query data, and reserve read-write keys for services that actively write to the API.
</Tip>

## Rotating a Compromised Key

If a key is exposed or you suspect unauthorized use, rotate it immediately:

<Steps>
  <Step title="Go to API Keys in Settings">
    Open **Settings → API Keys** in the Coherence Atlas dashboard.
  </Step>
  <Step title="Generate a Replacement Key">
    Create a new key with the same label and scope as the compromised key.
  </Step>
  <Step title="Update Your Applications">
    Replace the old key with the new one in all environments, secrets managers, and CI configurations that reference it.
  </Step>
  <Step title="Revoke the Old Key">
    Delete the compromised key from the dashboard. Revocation is **immediate** — any request using the old key will receive a `401 Unauthorized` response.
  </Step>
</Steps>

<Note>
  There is no grace period after revocation. Ensure your applications are updated before deleting the old key to avoid service interruption.
</Note>

## Security Best Practices

<Accordion title="Use environment variables, never hardcoded values">
  Store your API key in an environment variable (e.g., `COHERENCE_API_KEY`) and reference it in your application code. Never write the key literal into source files.

  ```bash
  export COHERENCE_API_KEY="ca_live_abc123xyz789"
  ```

  ```python
  import os
  api_key = os.environ["COHERENCE_API_KEY"]
  ```
</Accordion>

<Accordion title="Never commit API keys to version control">
  Ensure `.env` files and secrets configuration files are listed in your `.gitignore`. Use a secrets scanning tool in your CI pipeline to catch accidental key exposure before it reaches a remote repository.
</Accordion>

<Accordion title="Never expose keys in client-side code">
  API keys must only be used in server-side or backend contexts. Any key embedded in browser JavaScript, a mobile app binary, or a public repository should be considered compromised and rotated immediately.
</Accordion>

<Accordion title="Scope keys to the minimum required permissions">
  Issue separate keys for separate services. A read-only ingestion monitor does not need a read-write key. Scoping limits the blast radius if a key is ever exposed.
</Accordion>

<Warning>
  Never commit API keys to version control. If a key is accidentally pushed to a public or private repository, treat it as compromised and rotate it immediately — even if you delete the commit, the key may have been indexed or cached.
</Warning>

## Authentication Error Responses

The API returns authentication errors in the standard error envelope format.

**401 Unauthorized — missing or invalid API key:**

```json
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Invalid or missing API key. Provide a valid key in the Authorization header.",
    "details": {}
  },
  "meta": {
    "request_id": "req_03ghi",
    "timestamp": "2025-01-15T09:02:00Z"
  }
}
```

**403 Forbidden — valid key, insufficient scope:**

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "Your API key does not have permission to perform this action. A read-write key is required.",
    "details": {
      "required_scope": "read-write",
      "current_scope": "read-only"
    }
  },
  "meta": {
    "request_id": "req_04jkl",
    "timestamp": "2025-01-15T09:03:00Z"
  }
}
```

| Status | Code          | When it occurs                                                         |
|--------|---------------|------------------------------------------------------------------------|
| `401`  | `UNAUTHORIZED`| The `Authorization` header is absent, malformed, or the key is revoked |
| `403`  | `FORBIDDEN`   | The key is valid but its scope does not permit the requested operation  |

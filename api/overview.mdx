The Coherence Atlas REST API gives you programmatic access to the full platform — ingesting and querying signals, creating monitoring artifact records, managing structured review sessions, and traversing the knowledge graph. All interactions follow standard REST conventions over HTTPS, and every response is returned as JSON.

## Base URL

All API requests are made to the following base URL:

```text
https://api.coherencesystems.net/v1
```

## Versioning

The current API version is **v1**, reflected in the base URL path. Coherence Atlas follows a versioned release model — breaking changes are never introduced within a version. When a breaking change is required, a new version (e.g., `v2`) is published alongside the existing version, giving you time to migrate. Non-breaking additions (new fields, new endpoints) may be introduced within a version without notice.

<Note>
  Subscribe to the Coherence Systems Labs changelog to receive advance notice before a new API version is released.
</Note>

## HTTP Methods

The API uses standard HTTP methods for all operations:

| Method   | Purpose                                      |
|----------|----------------------------------------------|
| `GET`    | Retrieve a resource or list of resources     |
| `POST`   | Create a new resource                        |
| `PATCH`  | Partially update an existing resource        |
| `DELETE` | Remove a resource                            |

## Response Format

Every API response is a JSON object structured with a consistent envelope containing three top-level fields:

| Field   | Description                                                               |
|---------|---------------------------------------------------------------------------|
| `data`  | The primary payload for the request — a resource object or list           |
| `meta`  | Request metadata including a unique request ID and server-side timestamp  |
| `error` | Present only on failed requests; `null` or absent on success              |

**Successful response envelope:**

```json
{
  "data": { "..." : "..." },
  "meta": {
    "request_id": "req_01abc",
    "timestamp": "2025-01-15T09:00:00Z"
  }
}
```

**Error response envelope:**

```json
{
  "error": {
    "code": "INVALID_SIGNAL_SET",
    "message": "The signal set could not be validated. Check that all required fields are present.",
    "details": {
      "missing_fields": ["scale_levels"]
    }
  },
  "meta": {
    "request_id": "req_02def",
    "timestamp": "2025-01-15T09:01:00Z"
  }
}
```

The `error` object always includes:

<ResponseField name="error.code" type="string">
  A machine-readable error code identifying the category of failure (e.g., `INVALID_SIGNAL_SET`, `UNAUTHORIZED`).
</ResponseField>

<ResponseField name="error.message" type="string">
  A human-readable description of the error, suitable for logging and debugging.
</ResponseField>

<ResponseField name="error.details" type="object">
  An optional object providing structured context about the error — for example, a list of missing or invalid fields.
</ResponseField>

## HTTP Status Codes

The API uses standard HTTP status codes to indicate the outcome of every request.

| Code  | Status                  | Meaning                                                                 |
|-------|-------------------------|-------------------------------------------------------------------------|
| `200` | OK                      | The request succeeded; response body contains the requested data        |
| `201` | Created                 | A new resource was successfully created                                 |
| `400` | Bad Request             | The request was malformed or missing required parameters                |
| `401` | Unauthorized            | Authentication failed — API key is missing or invalid                   |
| `403` | Forbidden               | Authentication succeeded, but the key lacks permission for this action  |
| `404` | Not Found               | The requested resource does not exist                                   |
| `422` | Unprocessable Entity    | The request was well-formed but failed domain validation                |
| `429` | Too Many Requests       | Rate limit exceeded; slow down and retry after the indicated window     |
| `500` | Internal Server Error   | An unexpected error occurred on the server                              |

## Rate Limits

Each API key is permitted **1,000 requests per hour**. If your application exceeds this limit, the API returns a `429 Too Many Requests` response. The response headers include retry guidance:

| Header                  | Description                                          |
|-------------------------|------------------------------------------------------|
| `X-RateLimit-Limit`     | Total requests allowed per hour for your key         |
| `X-RateLimit-Remaining` | Requests remaining in the current window             |
| `X-RateLimit-Reset`     | Unix timestamp when the current window resets        |

<Tip>
  If you are running high-frequency batch ingestion, spread requests evenly across the rate window or contact Coherence Systems Labs to discuss elevated limits for your use case.
</Tip>

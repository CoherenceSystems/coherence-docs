Coherence Atlas is built on a specific vocabulary for talking about structural change in complex systems. Before you design a review workflow or interpret a drift assessment, it helps to have these concepts clear — not as abstract definitions, but as precise tools you will use repeatedly. This page walks through the full concept map, from what a registered view shows you to how artifact records build an auditable monitoring history.

## The Registered View

Every signal set you register in Coherence Atlas produces a **registered view** — a three-panel aligned display that puts observed motion, cross-scale structure, and state field geometry side by side. The key word is *registered*: all three panels are anchored to the same temporal context and the same system configuration, so you are never comparing across mismatched baselines.

The registered view does not replace your domain judgment. It gives that judgment a consistent, multi-scale frame to work within.

## The Four Capability Pillars

The four pillars map directly onto the four phases of how structural change in a complex system is typically encountered and understood.

<Accordion title="Context — Anchoring interpretation before it begins">
  **Context** is the first pillar because interpretation without a stated context produces noise, not insight. Before Coherence Atlas begins any analysis, it keeps four things visible: the system context (what kind of system, what operating conditions), the registered signals (which signals are active, what they measure), the prevailing conditions (any known environmental or operational factors), and the review question (what you are actually trying to understand).

  Context is not a preamble you fill in once and forget. It is an active constraint. If your review question is "is this system degrading?" and your context specifies nominal load conditions, the same drift pattern will carry a different meaning than if the context specifies an unusual stress event. Coherence Atlas keeps context co-visible with results so you do not drift from your own stated frame without noticing.

  **Typical use:** Framing a recurring monitoring session; defining what counts as a meaningful deviation for a given operational period.
</Accordion>

<Accordion title="Persistence — Distinguishing signal from coincidence">
  **Persistence** asks whether meaningful structure carries forward over time, rather than appearing only momentarily regular. A single anomalous reading is not persistent. A pattern that recurs across multiple review windows, at the same scale level, in a consistent structural form — that is persistent.

  Persistence is foundational because it separates noise from structure. High-frequency signal environments in particular produce many transient patterns that look organized at one moment and dissolve the next. Coherence Atlas evaluates persistence by tracking whether structural features are retained across temporal windows, not just whether they appear. A `persistence_flag` in the API indicates that the platform has detected a feature meeting this retention criterion.

  **Typical use:** Deciding whether a detected drift pattern warrants escalation; distinguishing a real degradation trend from measurement artifacts.
</Accordion>

<Accordion title="Drift — Reading gradual movement in context">
  **Drift** is the gradual movement, divergence, or degradation of a system relative to a stated reference state. Coherence Atlas reviews drift within context — meaning the same quantitative drift index can have different operational significance depending on what you told the platform the context is.

  Drift has direction. A system can drift toward a boundary (transition-adjacent drift), away from a reference (baseline divergence), or in ways that degrade internal structure without a clear directional signature (entropic drift). The `drift_index` returned by the API normalizes detected drift from 0.0 to 1.0, but the scale-specific results break this down by fine, mid, and broad levels so you can see where in the structural hierarchy the movement is concentrated.

  **Typical use:** Longitudinal review of an operational system; early warning review before scheduled maintenance; benchmarking analytical methods against synthetic drift datasets.
</Accordion>

<Accordion title="Transition — Building language for regime change">
  **Transition** refers to possible phase changes, regime shifts, and reorganizations that go beyond gradual drift into a qualitatively different structural state. Not every drift event leads to a transition. Coherence Atlas uses the `transition_candidate` flag to indicate when a system's state path geometry suggests it may be approaching a regime boundary.

  Transitions matter because the analytical language appropriate for a drifting system is not the same as for a system that has reorganized. Once a transition occurs, earlier persistence and drift assessments need to be re-read relative to the new regime, not the old one. Transition detection in Coherence Atlas is designed to give you time to build that language before the reorganization is complete — not simply to record it after the fact.

  **Typical use:** Preparing a deeper review session when a `transition_candidate` flag is returned; post-transition retrospective analysis; designing benchmark studies that include regime-shift scenarios.
</Accordion>

## The Knowledge Graph

Coherence Atlas uses a **scientific knowledge graph** as its structural backbone. Rather than storing signals as flat time-series records, the platform encodes relationships between signals, states, system structure, and temporal context as a graph — so queries can traverse relationships across time, scale, and state dimensions simultaneously.

<Note>
  The knowledge graph is what makes cross-scale structure possible. When you register a signal set with three scale levels, the graph builds edges between structural features at different scales, so the platform can detect whether a fine-scale irregularity has a corresponding mid-scale signature — or whether the broad-scale state is masking fine-scale disorder.
</Note>

You can query the knowledge graph directly using the `/graph` endpoint. This is particularly useful for research workflows where you want to inspect the inferred relationships between signals, or to validate that your signal set registration has been structured as expected.

## Signal Environments and Scale Levels

A **signal environment** is the dynamic, multi-signal setting in which a system is monitored. It is defined by the number and type of signals, their sample rates, their interrelationships, and the timescales at which meaningful structure appears.

Coherence Atlas organizes structural analysis across three scale levels:

| Scale Level | What It Captures | Typical Window |
|-------------|-----------------|----------------|
| **Fine** | Rapid local variation, transient events, high-frequency structure | Sub-second to seconds |
| **Mid** | Sustained patterns, inter-signal relationships, operational cycles | Minutes to hours |
| **Broad** | Long-run trends, regime-level organization, baseline stability | Hours to days |

You define which scale levels apply to your signal set at registration time. Not every domain has meaningful structure at every scale — a slow-moving environmental monitoring system may have nothing interpretable at fine scale, while a high-frequency trading signal environment may have no useful broad-scale structure within a single session.

## State Field and Basin Geometry

The **state field** is the geometric framework Coherence Atlas uses to represent where a system is and how it is moving through its possible behavioral states. Rather than treating system state as a single scalar value, the state field describes a landscape of possible configurations — some stable (basins), some unstable (boundaries), some transitional (paths between basins).

A **basin** is a region of the state field where a system naturally settles and returns to after small perturbations. Drift moves a system gradually across the basin. A regime shift moves the system out of one basin entirely and into another — or into a boundary region with no stable attractor.

<Info>
  Basin geometry is inferred from the registered signal set and updated as new data arrives. Early in a monitoring session, basin boundaries are estimated from prior structure; over time, they sharpen as the platform accumulates evidence about where the system consistently returns.
</Info>

The state field panel in the registered view shows the system's current position and recent path, so you can see at a glance whether it is moving toward or away from a basin boundary.

## Artifact Records and Monitoring Records

An **artifact record** is a single, auditable entry that captures the outcome of a review event — what signals were examined, what context was stated, what the assessment found, and any notes or escalations attached. Artifacts are created explicitly via `POST /artifacts` and are immutable once recorded.

A **monitoring record** is the cumulative history of artifact records for a signal set. It gives you a longitudinal audit trail of how a system has been reviewed over time — which is essential for compliance-adjacent workflows, research reproducibility, and post-incident retrospectives.

<Tip>
  Create an artifact record at the end of every review session, even when nothing unusual is found. A record of stable, non-drifting assessments is as valuable as a record of anomalies — it establishes the baseline against which future drift is measured.
</Tip>

## Concept Reference Table

The table below maps each core concept to what it measures and its most typical use case, giving you a quick reference as you build workflows.

| Concept | What It Measures | Typical Use Case |
|---------|-----------------|-----------------|
| **Registered View** | Three-panel aligned display of motion, structure, and state | Starting point for any review session |
| **Context** | System frame: signals, conditions, review question | Anchoring interpretation before analysis begins |
| **Persistence** | Whether structural features carry forward across time windows | Distinguishing real patterns from transient noise |
| **Drift** | Gradual movement, divergence, or degradation from a reference | Longitudinal monitoring; early-warning review |
| **Transition** | Possible phase change or regime reorganization | Regime boundary detection; post-reorganization review |
| **Knowledge Graph** | Relationships between signals, states, structure, and time | Cross-scale queries; method validation; graph inspection |
| **Signal Environment** | Dynamic multi-signal context of the monitored system | Defining registration scope and scale configuration |
| **Scale Level (Fine/Mid/Broad)** | Structural detail at a specific temporal resolution | Isolating where in the hierarchy drift is concentrated |
| **State Field** | Geometric landscape of system behavioral states | Visualizing basin position and transition proximity |
| **Basin** | Stable attractor region in the state field | Identifying normal operating regime |
| **Artifact Record** | Single auditable review outcome entry | Logging assessments; building monitoring history |
| **Monitoring Record** | Cumulative artifact history for a signal set | Audit trail; retrospective analysis; baseline calibration |

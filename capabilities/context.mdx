Before you interpret any signal movement or structural change, you need to establish what you are looking at and why. Context in Coherence Atlas keeps your review question, signal set, operating conditions, and known events visible and anchored throughout the entire analysis session. Without that anchor, a reading that looks like drift might simply be a well-understood operational mode — and the difference between those two conclusions carries real consequences.

## What Context Means in Coherence Atlas

Context is not metadata appended after the fact. It is the frame you construct before persistence or drift analysis begins, encoding everything that shapes what "normal" looks like for your system at a given time.

A context session captures:

<CardGroup cols={2}>
  <Card title="Review Question" icon="circle-question" href="/api/reviews">
    The explicit question guiding the analysis — what you are trying to determine about the system's behavior.
  </Card>
  <Card title="Signal Set" icon="signal" href="/api/signals">
    The registered signals under review, including their identifiers, sampling rates, and any known relationships.
  </Card>
  <Card title="Operating Conditions" icon="sliders" href="/api/reviews">
    The boundary conditions, load levels, environmental parameters, or regime labels that describe normal operation.
  </Card>
  <Card title="Time Window" icon="clock" href="/api/reviews">
    The start and end of the review period, including any sub-windows of particular interest.
  </Card>
  <Card title="Known Events" icon="calendar-check" href="/api/reviews">
    Logged interventions, resets, maintenance actions, or external disturbances that fall within the window.
  </Card>
</CardGroup>

## Why Context Matters

Interpretation without context produces misleading conclusions. A signal that appears to drift may be tracking a planned operational change. A structural pattern that looks degraded may reflect a known boundary condition. Coherence Atlas enforces the principle that every analysis runs inside a declared context — so that findings are always traceable to the conditions under which they were produced.

<Note>
  You must define a context session before running persistence or drift analysis. Attempting to call `/signals/{id}/persistence` or `/signals/{id}/drift` without a valid `context_id` will return a `422 Unprocessable Entity` error.
</Note>

## How to Define a Context Session

Context sessions are created through the `/reviews` endpoint. A review record holds all context fields and becomes the reference frame for every downstream query tied to it.

### API Reference

<ParamField body="review_question" type="string" required>
  The explicit question you are asking about this system. State it precisely — vague questions produce ambiguous interpretations.
</ParamField>

<ParamField body="signal_ids" type="array" required>
  List of signal identifiers to include in this review. Signals must already be registered via `/signals`.
</ParamField>

<ParamField body="time_window" type="object" required>
  An object with `start` and `end` as ISO 8601 timestamps defining the review period.
</ParamField>

<ParamField body="operating_conditions" type="object">
  Key-value pairs describing the system's operating state during the window — for example, load levels, configuration labels, or regime identifiers.
</ParamField>

<ParamField body="known_events" type="array">
  List of event objects, each with a `timestamp`, `type`, and `description`. Include maintenance actions, resets, or known disturbances.
</ParamField>

<ParamField body="tags" type="array">
  Optional string labels for organizing reviews across projects or teams.
</ParamField>

### Example: Creating a Context Session

The following example sets up a context session for a thermal monitoring study on an industrial system. The review question is explicit, the operating conditions record the load profile, and a known maintenance window is logged as an event.

```bash
POST https://api.coherencesystems.net/v1/reviews
Authorization: Bearer <your_token>
Content-Type: application/json
```

```json
{
  "review_question": "Does thermal signal coherence persist across the high-load cycle, or does it degrade relative to the baseline window?",
  "signal_ids": ["sig_therm_001", "sig_therm_002", "sig_therm_003"],
  "time_window": {
    "start": "2024-09-01T00:00:00Z",
    "end": "2024-09-30T23:59:59Z"
  },
  "operating_conditions": {
    "load_profile": "high",
    "ambient_temp_range_c": [18, 24],
    "cooling_mode": "active"
  },
  "known_events": [
    {
      "timestamp": "2024-09-14T08:30:00Z",
      "type": "maintenance",
      "description": "Scheduled cooling system inspection — 90-minute downtime."
    }
  ],
  "tags": ["thermal", "pilot-study-q3"]
}
```

A successful response returns the review record with its assigned `context_id`:

```json
{
  "review_id": "rev_8a3f2c1d",
  "context_id": "ctx_7b91e44f",
  "status": "active",
  "review_question": "Does thermal signal coherence persist across the high-load cycle, or does it degrade relative to the baseline window?",
  "signal_ids": ["sig_therm_001", "sig_therm_002", "sig_therm_003"],
  "time_window": {
    "start": "2024-09-01T00:00:00Z",
    "end": "2024-09-30T23:59:59Z"
  },
  "created_at": "2024-10-02T11:04:17Z"
}
```

Store the `context_id` — you will pass it as a parameter in all subsequent persistence, drift, and transition queries tied to this study.

## Retrieving a Context Session

You can retrieve any review record to confirm its context fields before running analysis.

```bash
GET https://api.coherencesystems.net/v1/reviews/rev_8a3f2c1d
Authorization: Bearer <your_token>
```

## Best Practices

<Accordion title="State the review question explicitly">
  A precise review question constrains interpretation. "Is there drift?" is too broad. "Does the coherence structure of the thermal signals degrade progressively after hour 48 of the high-load cycle?" is actionable. The question you record becomes part of the artifact record if you export findings.
</Accordion>

<Accordion title="Include known boundary conditions in operating_conditions">
  If your system has distinct operating regimes — load levels, configuration states, seasonal modes — encode them. Downstream analysis can then distinguish structural changes that fall inside expected regime variation from those that fall outside it.
</Accordion>

<Accordion title="Log known events before analysis, not after">
  Maintenance windows, resets, and external disturbances should be entered when you open the review, not added retroactively once you have seen an anomaly. Retroactive event logging introduces confirmation bias into the artifact record.
</Accordion>

<Accordion title="Scope signal sets to the review question">
  Include the signals that are directly relevant to your question. Registering every available signal creates noise in cross-scale analysis and slows graph queries. You can open a new review with an expanded signal set if the initial scope proves too narrow.
</Accordion>

Benchmarks in Coherence Atlas are structured scenarios with documented ground truth — they give you a controlled setting in which to evaluate whether a detection method is actually finding what it claims to find. Before applying any method to real operational data, a well-designed benchmark tells you where the method performs reliably, where its sensitivity boundaries lie, and what claim boundaries are defensible. This guide walks you through designing, registering, and running benchmarks for drift, degradation, and transition behavior.

<Tip>
  Run benchmarks before applying your chosen methods to real data. A benchmark with known ground truth is the most efficient way to validate that your configuration is calibrated to the signal environment you care about — and to document those validation results as evidence for method choices.
</Tip>

## What a Benchmark Is

A Coherence Atlas benchmark is a structured evaluation scenario consisting of:

- **Synthetic signal generation parameters** that produce a signal set with known, designed-in behavior
- **Ground truth labels** marking exactly when and where drift, degradation, or transition events occur
- **Evaluation criteria** defining what a correct detection looks like and what constitutes a false positive or missed event
- **Claim boundaries** stating what the benchmark is designed to test and what it is explicitly not testing

Benchmarks are not general stress tests. Each benchmark is scoped to a specific question about method behavior.

## The Three Benchmark Types

<CardGroup cols={3}>
  <Card title="Drift Benchmarks" icon="chart-line">
    Test whether your drift detection configuration correctly identifies gradual movement and divergence across scale levels. Ground truth includes the onset time, rate, and scale signature of the designed-in drift.
  </Card>
  <Card title="Degradation Benchmarks" icon="arrow-trend-down">
    Test whether structural degradation — loss of coherence over time — is detected at the right moment and at the right scale. Ground truth includes the degradation onset and the scale levels affected.
  </Card>
  <Card title="Transition Benchmarks" icon="shuffle">
    Test whether candidate transition windows — phase changes and regime shifts — are correctly identified within tolerable timing windows. Ground truth includes the designed transition point and the expected state-field signature.
  </Card>
</CardGroup>

## Creating a Benchmark

<Steps>

  ### Define the Scenario Parameters

  Specify what the benchmark is testing, the signal type and environment it uses, the expected behavior it encodes, and the duration of the synthetic record.

  Key decisions at this stage:
  - **Benchmark type** — drift, degradation, or transition
  - **Signal type** — continuous, discrete, or mixed
  - **Number of signals** — how many signals participate in the designed behavior
  - **Duration** — how long the synthetic record runs
  - **Event timing** — when within the record the designed behavior begins and ends
  - **Scale signature** — which scale levels (fine, mid, broad) should be affected

  Document these decisions explicitly. They become part of the claim boundary: what you can conclude from this benchmark is limited to the parameter space it covers.

  ### Configure Synthetic Signal Generation

  Use the `/benchmarks` endpoint to configure your synthetic signal generation. The `ground_truth` block defines the exact event you are testing — Coherence Atlas uses it to score detection results.

  ```http
  POST https://api.coherencesystems.net/v1/benchmarks
  Authorization: Bearer <your_token>
  Content-Type: application/json
  ```

  ```json
  {
    "name": "Mid-scale drift onset — cluster A",
    "type": "drift",
    "description": "Tests detection of gradual mid-scale drift beginning at t=72h in a two-signal continuous environment.",
    "signal_config": {
      "signal_count": 2,
      "signal_type": "continuous",
      "duration_hours": 168,
      "noise_level": "low",
      "base_coherence": 0.80
    },
    "ground_truth": {
      "event_type": "drift",
      "onset_hour": 72,
      "end_hour": 120,
      "scale_signature": ["mid"],
      "drift_rate": "gradual",
      "magnitude": 0.55
    },
    "evaluation_criteria": {
      "detection_window_tolerance_hours": 6,
      "required_scale_match": true,
      "false_positive_budget": 1
    }
  }
  ```

  A successful registration returns a `benchmark_id` and the generated synthetic signal set identifier.

  ```json
  {
    "benchmark_id": "bmark_8a1f3c90",
    "signal_set_id": "sset_synth_d4b2e7a1",
    "status": "ready",
    "ground_truth_locked": true
  }
  ```

  Note that `ground_truth_locked: true` confirms the ground truth labels are sealed before you run detection — results cannot be fitted retrospectively to the known answer.

  ### Set Evaluation Criteria and Claim Boundaries

  Evaluation criteria define what a correct result looks like. Claim boundaries define what the benchmark result is and is not evidence for.

  <Accordion title="Evaluation criteria reference">
    | Field | Description |
    |---|---|
    | `detection_window_tolerance_hours` | How many hours early or late a detection can be and still count as correct |
    | `required_scale_match` | Whether the detected scale signature must match the ground truth scale levels |
    | `false_positive_budget` | Maximum number of false positives tolerated before the run is scored as failing |
    | `min_confidence_level` | Minimum confidence level a detection must carry to be counted |
  </Accordion>

  Write your claim boundaries before running. A well-scoped claim boundary for the example above might read:

  > "A passing result on this benchmark supports the claim that mid-scale drift detection is reliable within ±6 hours for gradual-rate drift in low-noise two-signal environments. It does not support claims about fine-scale or broad-scale drift, high-noise environments, or drift rates outside the gradual range."

  Record this language in your benchmark configuration or in an associated artifact record — it becomes the evidence basis for method validation decisions.

  ### Register the Benchmark Scenario via the API

  If you need to update scenario metadata or claim boundaries before running, use the PATCH endpoint:

  ```http
  PATCH https://api.coherencesystems.net/v1/benchmarks/bmark_8a1f3c90
  Authorization: Bearer <your_token>
  Content-Type: application/json
  ```

  ```json
  {
    "claim_boundary": "A passing result supports mid-scale gradual drift detection reliability in low-noise two-signal environments within ±6 hours. Does not generalize to other scale levels, noise conditions, or drift rates.",
    "tags": ["validation", "mid-scale", "drift", "pre-deployment"]
  }
  ```

  ### Run the Benchmark and Compare Results

  Trigger benchmark execution. Coherence Atlas runs your configured detection methods against the synthetic signal set and scores results against the sealed ground truth.

  ```http
  POST https://api.coherencesystems.net/v1/benchmarks/bmark_8a1f3c90/run
  Authorization: Bearer <your_token>
  Content-Type: application/json
  ```

  ```json
  {
    "detection_config": {
      "persistence_threshold": 0.65,
      "drift_sensitivity": "moderate",
      "scale_levels": ["fine", "mid", "broad"]
    }
  }
  ```

  Retrieve results once the run completes:

  ```http
  GET https://api.coherencesystems.net/v1/benchmarks/bmark_8a1f3c90/results
  Authorization: Bearer <your_token>
  ```

  ```json
  {
    "benchmark_id": "bmark_8a1f3c90",
    "run_id": "run_5c3d9f12",
    "status": "complete",
    "score": {
      "detection_correct": true,
      "detected_onset_hour": 74,
      "tolerance_met": true,
      "scale_match": true,
      "false_positives": 0,
      "overall": "pass"
    },
    "notes": "Drift onset detected at hour 74 — within 6-hour tolerance of ground truth onset at hour 72. Scale signature correctly identified as mid-scale only."
  }
  ```

</Steps>

## Best Practices for Disciplined Claim Boundaries

<Accordion title="Keep each benchmark narrowly scoped">
  A benchmark that tests too many variables at once produces results that are difficult to interpret. Design one benchmark per question: one signal type, one scale level of interest, one event type. Build a library of narrow benchmarks rather than a small number of broad ones.
</Accordion>

<Accordion title="Seal ground truth before running">
  Always confirm `ground_truth_locked: true` before triggering a run. Retrospectively adjusting ground truth to match results invalidates the benchmark as evidence.
</Accordion>

<Accordion title="Document claim boundaries in the benchmark record">
  Claim boundaries written before running are more credible than boundaries written after seeing results. Include them in the benchmark registration payload or in an associated artifact record.
</Accordion>

<Accordion title="Version your benchmark configurations">
  As your methods evolve, re-run the same benchmark configurations to track whether changes improve or degrade detection reliability. Use the `tags` field to group related benchmark versions.
</Accordion>

<Accordion title="Use benchmark results as evidence, not proof">
  A passing benchmark result is evidence that a method performs reliably in the tested parameter space. It is not proof of general reliability. Reference the claim boundary every time you cite a benchmark result.
</Accordion>

The Coherence Atlas API is organized around six primary object types. Each type maps to a distinct stage in the analysis workflow — from ingesting signals through running review sessions to producing auditable artifact records. Understanding the data model before you write API calls will save you time setting up signal sets and interpreting the objects returned in review and artifact responses.

## Object Overview

<CardGroup cols={3}>
  <Card title="Signal Set" icon="layer-group">

## Signal Set

A signal set is a named, domain-tagged collection of related signals that are ingested and analyzed together. When you register a signal set, Coherence Atlas creates a corresponding node in the knowledge graph and prepares the scale-level views specified in `scale_levels`.

**Endpoint:** `POST /signals/sets` · `GET /signals/sets/{id}`

```json
{
  "id": "sset_01j8kx4p9r2mna7vqz3fte6d",
  "name": "Reactor Loop A — Thermal Sensors",
  "domain": "engineered_systems",
  "scale_levels": ["fine", "mid", "broad"],
  "signals": [
    "sig_01j8kx4p9r2mna7vqz3fte6e",
    "sig_01j8kx4p9r2mna7vqz3fte6f"
  ],
  "created_at": "2025-03-14T09:22:11Z",
  "status": "active"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | Auto-assigned | Unique identifier for the signal set. |
| `name` | string | Required | Human-readable label for this collection. |
| `domain` | string | Required | Application domain tag (e.g., `engineered_systems`, `research_instrumentation`). |
| `scale_levels` | array of strings | Required | One or more of `"fine"`, `"mid"`, `"broad"`. At least one is required. |
| `signals` | array of strings | Optional | Signal IDs belonging to this set. Populated after individual signal registration. |
| `created_at` | string (ISO 8601) | Auto-assigned | Timestamp of signal set creation. |
| `status` | string | Auto-assigned | Lifecycle status: `active`, `archived`, or `processing`. |

<Note>
  You must specify at least one `scale_level` at creation time. Scale levels cannot be removed after signals are ingested, though you can add new levels.
</Note>

## Signal

A signal is a single time-series channel registered within a signal set. Each signal carries unit and sampling metadata used by Coherence Atlas to align channels in the registered view and construct cross-scale structure.

**Endpoint:** `POST /signals` · `GET /signals/{id}`

```json
{
  "id": "sig_01j8kx4p9r2mna7vqz3fte6e",
  "signal_set_id": "sset_01j8kx4p9r2mna7vqz3fte6d",
  "name": "Coolant Inlet Temperature",
  "unit": "celsius",
  "sample_rate_hz": 10.0,
  "tags": ["thermal", "inlet", "primary_loop"]
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | Auto-assigned | Unique identifier for this signal. |
| `signal_set_id` | string | Required | The parent signal set this signal belongs to. |
| `name` | string | Required | Human-readable label for this channel. |
| `unit` | string | Required | Physical or logical unit of the signal values (e.g., `"celsius"`, `"mV"`, `"dimensionless"`). |
| `sample_rate_hz` | number | Required | Nominal sampling rate in Hz. |
| `tags` | array of strings | Optional | Freeform labels used to filter and group signals in the API and registered view. |

<Tip>
  Use consistent tags across signals in the same set — for example, `"thermal"` or `"pressure"` — so that cross-scale queries on the `/graph` endpoint can group by tag rather than requiring you to enumerate signal IDs.
</Tip>

## Review Session

A review session is a scoped analysis session anchored to a context object. Opening a session records your review question and conditions before any interpretation begins, keeping that context attached to every finding you generate. Sessions move through a lifecycle: `open` → `in_review` → `finalized`.

**Endpoint:** `POST /reviews` · `GET /reviews/{id}`

```json
{
  "id": "rev_01j8m2nq7t5pbz9cxw0gkr3y",
  "context": {
    "review_question": "Does thermal drift in the primary loop exceed the established baseline during the Q1 run period?",
    "time_range": {
      "start": "2025-01-01T00:00:00Z",
      "end": "2025-03-31T23:59:59Z"
    },
    "known_conditions": [
      "Scheduled maintenance window at 2025-02-14",
      "Ambient temperature spike recorded 2025-01-19"
    ],
    "signal_set_id": "sset_01j8kx4p9r2mna7vqz3fte6d"
  },
  "status": "in_review",
  "created_at": "2025-04-02T08:15:00Z",
  "updated_at": "2025-04-02T11:43:22Z"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | Auto-assigned | Unique identifier for this review session. |
| `context` | object | Required | Embedded context object (see below). |
| `status` | string | Auto-assigned | `open`, `in_review`, or `finalized`. |
| `created_at` | string (ISO 8601) | Auto-assigned | Timestamp of session creation. |
| `updated_at` | string (ISO 8601) | Auto-assigned | Timestamp of most recent update. |

### Context Object

The context object is embedded in every review session and artifact record. It is the structured declaration of what you are reviewing, over what period, and under what known conditions.

<Expandable title="Context object fields">
  ```json
  {
    "review_question": "Does thermal drift in the primary loop exceed the established baseline during the Q1 run period?",
    "time_range": {
      "start": "2025-01-01T00:00:00Z",
      "end": "2025-03-31T23:59:59Z"
    },
    "known_conditions": [
      "Scheduled maintenance window at 2025-02-14",
      "Ambient temperature spike recorded 2025-01-19"
    ],
    "signal_set_id": "sset_01j8kx4p9r2mna7vqz3fte6d"
  }
  ```

  | Field | Type | Required | Description |
  |---|---|---|---|
  | `review_question` | string | Required | A plain-language statement of what this session is investigating. |
  | `time_range` | object | Required | Object with `start` and `end` fields as ISO 8601 timestamps. |
  | `time_range.start` | string (ISO 8601) | Required | Inclusive start of the review window. |
  | `time_range.end` | string (ISO 8601) | Required | Inclusive end of the review window. |
  | `known_conditions` | array of strings | Optional | List of known external conditions or events relevant to the review period. |
  | `signal_set_id` | string | Required | The signal set to analyze in this session. |
</Expandable>

<Note>
  The `review_question` field is required and not just a label — it is embedded in every artifact record so that findings remain traceable to the question that motivated them.
</Note>

## Artifact Record

An artifact record is the auditable output produced when you finalize a review session. It captures findings, claim boundaries, and links back to the review session and knowledge graph nodes referenced during analysis. Artifact records are the primary deliverable of a diligence or operational review workflow.

**Endpoint:** `POST /artifacts` · `GET /artifacts/{id}`

```json
{
  "id": "art_01j8p5rw2v6qce4hbn7tmx9k",
  "review_session_id": "rev_01j8m2nq7t5pbz9cxw0gkr3y",
  "findings": {
    "persistence": {
      "summary": "Thermal structure is persistent across the fine and mid scales for the first 60% of registered progression. Broad-scale coherence degrades after position 62.",
      "score": 0.71
    },
    "drift": {
      "summary": "A gradual upward drift of approximately 1.4°C relative to baseline is detectable from position 38 onward at the mid scale.",
      "onset_position": 38
    },
    "transition_windows": [
      {
        "start_position": 61,
        "end_position": 67,
        "confidence": "moderate",
        "note": "Coincides with the recorded ambient temperature spike."
      }
    ]
  },
  "claim_boundaries": [
    "Findings are scoped to the Q1 2025 run period only and do not extend to prior operating cycles.",
    "The transition window at positions 61–67 is flagged as a candidate; causal attribution to the ambient spike is not established by this record."
  ],
  "created_at": "2025-04-02T14:10:55Z"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | Auto-assigned | Unique identifier for this artifact record. |
| `review_session_id` | string | Required | The review session this record finalizes. |
| `findings` | object | Required | Structured findings object (see below). |
| `claim_boundaries` | array of strings | Required | One or more explicit statements of what the evidence supports and does not support. |
| `created_at` | string (ISO 8601) | Auto-assigned | Timestamp of artifact record creation. |

### Findings Object

<Expandable title="Findings object fields">
  The `findings` object is flexible — it mirrors the analysis types run in the session. The fields below reflect standard findings keys.

  | Field | Type | Description |
  |---|---|---|
  | `findings.persistence` | object | Persistence summary and numeric score (0–1). |
  | `findings.persistence.summary` | string | Plain-language description of persistence findings. |
  | `findings.persistence.score` | number | Scalar persistence score from 0 (no persistence) to 1 (full persistence). |
  | `findings.drift` | object | Drift summary and onset position. |
  | `findings.drift.summary` | string | Plain-language description of detected drift. |
  | `findings.drift.onset_position` | integer | Registered progression position (0–100) where drift onset was detected. |
  | `findings.transition_windows` | array of objects | List of detected candidate transition windows. |
  | `findings.transition_windows[].start_position` | integer | Registered progression start of the transition window (0–100). |
  | `findings.transition_windows[].end_position` | integer | Registered progression end of the transition window (0–100). |
  | `findings.transition_windows[].confidence` | string | Confidence level: `low`, `moderate`, or `high`. |
  | `findings.transition_windows[].note` | string | Optional note linking the window to a known condition or signal event. |
</Expandable>

<Warning>
  You must include at least one `claim_boundary` string when creating an artifact record. Submissions with an empty `claim_boundaries` array will be rejected with a `422` response.
</Warning>

## Benchmark Scenario

A benchmark scenario is a synthetic or parameterized configuration used to validate Coherence Atlas analysis behavior against ground truth. Benchmark scenarios are used by researchers and partners to test detection sensitivity, compare methods, and assess how the platform responds to known drift, degradation, or transition patterns.

**Endpoint:** `POST /reviews/benchmarks` · `GET /reviews/benchmarks/{id}`

```json
{
  "id": "bench_01j8q7sx4y8raf2nbk5uvw1j",
  "type": "drift",
  "parameters": {
    "drift_onset_position": 40,
    "drift_rate": 0.05,
    "noise_level": "low",
    "signal_count": 6,
    "scale_levels": ["fine", "mid"]
  },
  "criteria": {
    "detection_required_by_position": 55,
    "false_positive_tolerance": 0.10
  },
  "status": "ready"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | Auto-assigned | Unique identifier for this benchmark scenario. |
| `type` | string | Required | Scenario category: `"drift"`, `"degradation"`, or `"transition"`. |
| `parameters` | object | Required | Configuration parameters specific to the scenario type (see below). |
| `criteria` | object | Required | Pass/fail criteria used to evaluate analysis output against ground truth. |
| `status` | string | Auto-assigned | `ready`, `running`, or `complete`. |

### Parameters and Criteria Objects

<Expandable title="Benchmark parameters and criteria fields">
  **Common parameter fields (all types):**

  | Field | Type | Description |
  |---|---|---|
  | `signal_count` | integer | Number of synthetic signals generated for the scenario. |
  | `scale_levels` | array of strings | Scale levels active in this scenario. |
  | `noise_level` | string | Background noise level: `"low"`, `"medium"`, or `"high"`. |

  **Drift-specific parameters:**

  | Field | Type | Description |
  |---|---|---|
  | `drift_onset_position` | integer | Registered progression position where drift begins (0–100). |
  | `drift_rate` | number | Rate of change per unit of registered progression. |

  **Transition-specific parameters:**

  | Field | Type | Description |
  |---|---|---|
  | `transition_position` | integer | Registered progression position of the ground-truth transition. |
  | `transition_sharpness` | string | How abrupt the transition is: `"sharp"`, `"gradual"`. |

  **Common criteria fields:**

  | Field | Type | Description |
  |---|---|---|
  | `detection_required_by_position` | integer | The latest registered progression position by which detection must occur to pass. |
  | `false_positive_tolerance` | number | Maximum acceptable false-positive rate (0–1). |
</Expandable>

<Tip>
  Use `type: "transition"` benchmark scenarios to calibrate transition window detection sensitivity before applying the platform to live operational data. Start with `noise_level: "low"` to establish a clean baseline, then increase noise to assess robustness.
</Tip>

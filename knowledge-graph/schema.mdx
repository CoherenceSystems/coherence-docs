The Coherence Atlas knowledge graph schema defines the structure that every registered signal set, state field, and review session must conform to. Understanding the schema before ingestion ensures that your signals are correctly positioned in the graph — connected to the right scale levels, carrying the properties needed for structural queries, and compatible with the Drift and Transition review workflows that depend on well-formed graph topology.

## Top-Level Object Types

The schema recognizes four top-level object types. Each maps to a category of node in the graph.

| Object Type | Graph Node Type | Purpose |
|---|---|---|
| `signal_set` | `SignalNode` | Defines one or more signals being registered together |
| `state_field` | `StateNode` | Defines known states and basin structure for a system |
| `scale_config` | `ScaleNode` | Declares the scale levels and their signal assignments |
| `review_session` | `ReviewNode` | Defines a bounded review context with a stated question |

## Signal Set Schema

A `signal_set` object registers one or more signals into the graph. The fields below apply to each signal within the set.

### Required Fields

| Field | Type | Description |
|---|---|---|
| `name` | `string` | Unique, human-readable identifier for the signal (e.g., `"reactor-temperature-array"`) |
| `domain` | `string` | Application domain. Allowed values: `engineered_systems`, `research_instrumentation`, `simulation`, `operational_review` |
| `scale_levels` | `array[string]` | One or more scale levels at which this signal is observed. Must include at least one of `fine`, `mid`, `broad` |
| `registered_at` | `ISO 8601 datetime` | Registration timestamp. Must be a valid UTC datetime |

### Optional Fields

| Field | Type | Description |
|---|---|---|
| `description` | `string` | Free-text description of what the signal measures |
| `units` | `string` | Physical or logical units of the signal value |
| `sampling_rate_hz` | `float` | Expected sampling frequency in hertz |
| `tags` | `array[string]` | Free-form tags for filtering and grouping |
| `threshold_config` | `object` | Configuration for automatic `EventNode` creation on threshold crossings (see below) |

### Threshold Configuration

When you include a `threshold_config` object on a signal, Coherence Atlas automatically creates `EventNode` entries when the signal crosses the defined boundaries. This powers automatic temporal edge construction without requiring manual event registration.

| Field | Type | Required | Description |
|---|---|---|---|
| `upper` | `float` | No | Upper threshold value |
| `lower` | `float` | No | Lower threshold value |
| `event_type` | `string` | Yes (if any threshold set) | Label for the generated event (e.g., `"threshold_crossing"`) |
| `debounce_ms` | `integer` | No | Minimum milliseconds between successive events to prevent noise-driven duplication |

## State Field Schema

A `state_field` object defines the known states of a system and organizes them into basins. Registering a state field explicitly gives Coherence Atlas the structural vocabulary needed to assign `BELONGS_TO_BASIN` edges and recognize `TRANSITIONS_TO` patterns.

### Required Fields

| Field | Type | Description |
|---|---|---|
| `system_id` | `string` | Identifier linking this state field to a registered signal set or system entity |
| `states` | `array[object]` | List of state definitions (see state object fields below) |

### State Object Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | `string` | Yes | Unique state identifier |
| `label` | `string` | Yes | Human-readable state label |
| `basin_id` | `string` | Yes | Identifier of the containing basin |
| `is_basin_root` | `boolean` | No | If `true`, this state is the canonical center of its basin |
| `stability_score` | `float` | No | Initial stability estimate (0–1); updated by the platform over time |

## Scale Configuration Schema

A `scale_config` object declares how your signals are distributed across the three scale levels. While `scale_levels` on individual signals handles simple cases, a `scale_config` is required when you need to define scale-level descriptions or set relative signal weights.

### Required Fields

| Field | Type | Description |
|---|---|---|
| `signal_set_id` | `string` | ID of the signal set this configuration applies to |
| `levels` | `array[object]` | One object per scale level (see level object fields below) |

### Level Object Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `level` | `string` | Yes | One of `fine`, `mid`, `broad` |
| `description` | `string` | No | Human-readable description of what this scale captures |
| `signal_ids` | `array[string]` | Yes | Signal IDs assigned to this level |
| `weights` | `object` | No | Map of `signal_id` → `float` (0–1) setting relative structural contribution |

### Scale Level Semantics

The three scale levels map to distinct analytical resolutions in Coherence Atlas:

<Tabs>
  <Tab title="Fine">
    Fine-scale structure captures short-duration, high-frequency signal behavior. Use `fine` for individual sensor readings, sub-second events, and local anomalies. Fine-scale nodes feed the `PRECEDES` edge construction that drives temporal sequence analysis.
  </Tab>
  <Tab title="Mid">
    Mid-scale structure captures behavioral patterns that emerge over seconds to minutes — moving averages, windowed correlations, and local drift trends. Mid-scale is where `CORRELATES_WITH` edges are most densely formed and where early drift signatures typically become visible.
  </Tab>
  <Tab title="Broad">
    Broad-scale structure captures system-wide configurations and long-duration regime characteristics. Broad-scale nodes are the primary anchors for `BELONGS_TO_BASIN` and `TRANSITIONS_TO` edges. Transition review operates predominantly at this scale.
  </Tab>
</Tabs>

## Validation Rules

Coherence Atlas validates every schema object at registration time. Violations return a `422 Unprocessable Entity` response with a structured error payload identifying the offending field.

<Accordion title="Required field missing">
  If any required field is absent, registration is rejected. The error response identifies the missing field by name and the object type it belongs to.

  ```json
  {
    "error": "schema_validation_failed",
    "detail": "Missing required field 'scale_levels' on signal object 'reactor-temperature-array'."
  }
  ```
</Accordion>

<Accordion title="Invalid scale_levels value">
  `scale_levels` must be an array containing one or more of `fine`, `mid`, `broad`. Any other value causes rejection.

  ```json
  {
    "error": "schema_validation_failed",
    "detail": "Invalid scale level 'micro' — allowed values are 'fine', 'mid', 'broad'."
  }
  ```
</Accordion>

<Accordion title="Invalid domain value">
  The `domain` field on a signal must match one of the allowed domain identifiers. Free-text domains are not permitted.

  ```json
  {
    "error": "schema_validation_failed",
    "detail": "Invalid domain 'industrial' — allowed values are 'engineered_systems', 'research_instrumentation', 'simulation', 'operational_review'."
  }
  ```
</Accordion>

<Accordion title="Basin root conflict">
  Each basin may have at most one root state (`is_basin_root: true`). Registering a second root for the same `basin_id` is rejected.

  ```json
  {
    "error": "schema_validation_failed",
    "detail": "Basin 'basin_stable_A' already has a registered root state. Set 'is_basin_root' to false or update the existing root."
  }
  ```
</Accordion>

<Warning>
  Schema validation failures do not partially register your data. The entire registration request is rejected atomically — no nodes or edges are created until the full schema passes validation.
</Warning>

## Full Schema Example

The following is a complete, valid schema definition for a signal set covering an engineered system with temperature and pressure signals, a two-state field, and explicit scale configuration.

```json
{
  "signal_set": {
    "signals": [
      {
        "name": "reactor-temperature-array",
        "domain": "engineered_systems",
        "description": "Multi-point temperature readings across reactor vessel",
        "units": "celsius",
        "sampling_rate_hz": 10.0,
        "scale_levels": ["fine", "mid", "broad"],
        "registered_at": "2025-01-15T09:00:00Z",
        "tags": ["thermal", "primary-loop"],
        "threshold_config": {
          "upper": 420.0,
          "lower": 280.0,
          "event_type": "threshold_crossing",
          "debounce_ms": 500
        }
      },
      {
        "name": "reactor-pressure-primary",
        "domain": "engineered_systems",
        "description": "Primary loop pressure sensor",
        "units": "bar",
        "sampling_rate_hz": 5.0,
        "scale_levels": ["fine", "mid"],
        "registered_at": "2025-01-15T09:00:00Z",
        "tags": ["pressure", "primary-loop"]
      }
    ]
  },
  "state_field": {
    "system_id": "sys_reactor_unit_01",
    "states": [
      {
        "id": "state_nominal_02",
        "label": "nominal-operating-range",
        "basin_id": "basin_stable_A",
        "is_basin_root": true,
        "stability_score": 0.95
      },
      {
        "id": "state_elevated_threshold_01",
        "label": "elevated-threshold-region",
        "basin_id": "basin_transition_B",
        "is_basin_root": true,
        "stability_score": 0.42
      }
    ]
  },
  "scale_config": {
    "signal_set_id": "sigset_reactor_01",
    "levels": [
      {
        "level": "fine",
        "description": "Sub-second sensor readings and threshold events",
        "signal_ids": ["reactor-temperature-array", "reactor-pressure-primary"]
      },
      {
        "level": "mid",
        "description": "60-second rolling patterns and cross-signal correlation",
        "signal_ids": ["reactor-temperature-array", "reactor-pressure-primary"],
        "weights": {
          "reactor-temperature-array": 0.7,
          "reactor-pressure-primary": 0.3
        }
      },
      {
        "level": "broad",
        "description": "System-wide configuration and regime membership",
        "signal_ids": ["reactor-temperature-array"]
      }
    ]
  }
}
```

## Schema Versioning

<Note>
  Coherence Atlas schema definitions are versioned. When you register a signal set or state field, the platform records the schema version in effect at registration time. If the schema evolves in a future platform release, your existing registered objects remain valid under the version they were registered with. The API response for every graph object includes a `schema_version` field indicating which version governs that object's structure. Review the changelog before migrating existing signal sets to a new schema version.
</Note>
